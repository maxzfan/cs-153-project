# feat: Revamp Stripe Permissions & Reconnect Sandbox

## Overview

Enforce plan-based sharing restrictions at the backend level and migrate Stripe to a new test sandbox. Currently, **any authenticated user can create shared projects, invite members, and use cloud sync regardless of subscription status**. The "5 team members" Pro limit and sharing restrictions are purely UI copy with zero enforcement.

This plan adds backend middleware to gate collaboration features behind an active subscription, swaps Stripe credentials to a new sandbox account, creates a $10/month product, and verifies the full purchase flow end-to-end.

## Problem Statement / Motivation

1. **No backend enforcement of plan-gated features.** Free users can share projects, invite unlimited members, and sync to the cloud. The three-tier pricing model (Free/Pro/Enterprise) is cosmetic only.
2. **Stripe connected to wrong/old sandbox.** The hardcoded price ID `price_1SpIuQBU9neqC79tYoTbDCck` in `src/pages/Dashboard.tsx:60` belongs to a different Stripe account and needs to be replaced.
3. **Need to test the $10 purchase flow** end-to-end with the new sandbox.

## Proposed Solution

### Phase 1: Backend Subscription Enforcement

**New middleware: `verifySubscription`** in `backend/middleware/auth.js`

Create a middleware that queries the `subscriptions` table for an active plan (`status = 'active'`) for the authenticated user. Returns 403 with a clear error shape if no active subscription exists.

```javascript
// backend/middleware/auth.js
const verifySubscription = (requiredPlans = ['student', 'enterprise']) => {
  return async (req, res, next) => {
    const userId = req.user.id;
    const { data } = await supabase
      .from('subscriptions')
      .select('plan, status')
      .eq('user_id', userId)
      .eq('status', 'active')
      .single();

    if (!data || !requiredPlans.includes(data.plan)) {
      return res.status(403).json({
        error: 'subscription_required',
        message: 'An active subscription is required for this feature',
        requiredPlans
      });
    }
    req.subscription = data;
    next();
  };
};
```

**Apply to these routes:**

| Route | File | Rationale |
|-------|------|-----------|
| `POST /api/projects` | `backend/routes/projects.js` | Registering a project for cloud sharing |
| `POST /api/projects/:projectId/members` | `backend/routes/projects.js` | Inviting team members |
| `POST /api/projects/:projectId/sync/push-url` | `backend/routes/sync.js` | Pushing commits to cloud |
| `POST /api/projects/:projectId/sync/push-tree` | `backend/routes/sync.js` | Pushing tree state |

**NOT gated** (allow free collaborators to read):

| Route | Rationale |
|-------|-----------|
| `GET /api/projects/:projectId/sync/pull-url` | Invited viewers should be able to pull |
| `GET /api/projects/:projectId/sync/pull-content` | Same — read access for invited members |
| `GET /api/projects/:projectId/sync/list` | Listing commits for read access |
| `GET /api/projects/:projectId/sync/tree-etag` | Checking tree state |
| `GET /api/projects/:projectId/members` | Viewing members |

**Decision: Only the project owner/inviter needs a paid plan.** Free users can be invited as viewers/editors to a paid user's project. The subscription check applies to the *acting user* on write operations, not to all project members.

**Lapsed subscription behavior:** When an owner's subscription lapses (`canceled` or `past_due`), existing collaborators retain read-only access (pull). The owner loses push and invite capabilities until they resubscribe. No existing data is deleted.

### Phase 3: Create Stripe Product & Price

Using the Stripe CLI or Dashboard on the new sandbox account:

```bash

  --product=<product_id> \
```

### Phase 4: Enable Feature Flags

Set both feature flags to `true` so the UI is visible and subscription checks do the real gating:

```env

VITE_FEATURES_PAYMENTS=true
```

Without this, the team/sharing UI is hidden at build time and the backend enforcement is unreachable from the UI.

### Phase 5: Frontend Handling of 403

Update `CloudSyncContext` and project settings to handle the new `subscription_required` error:

- When a sync push or member invite returns 403 with `error: 'subscription_required'`, show a toast/dialog prompting the user to upgrade
- Link directly to `/dashboard` pricing page
- Do NOT rely on `features.team` flag to hide sharing UI — show it but gate the action with a clear upgrade prompt

## Technical Considerations

- **Webhook ordering:** `express.raw()` for `/api/stripe/webhook` must stay before `express.json()` in `backend/server.js:92-95`. Do not reorder.
- **API version:** `backend/server.js:49` pins Stripe API version to `2024-12-18.acacia`. The new sandbox account may default to a newer version. Keep the pin to avoid payload mismatches.
- **Plan naming:** Database stores `'student'` but UI shows "Pro". Keep `'student'` internally to avoid a migration. The mapping is in `src/pages/Settings.tsx:62-68`.
- **`hasVerifiedPlan` is dead code** in AuthContext — exposed but never consumed. Can be cleaned up but not blocking.
- **Subscription upsert:** `create-subscription-intent` upserts on `user_id` conflict (`backend/routes/stripe.js:348`), so old subscription rows from the previous Stripe sandbox will be overwritten. This is fine.
- **Enterprise CTA:** The Enterprise pricing card's `onPlanSelect` handler will fail if `VITE_STRIPE_ENTERPRISE_PRICE_ID` is empty. Either disable the CTA or add a "Contact sales" fallback.

## System-Wide Impact

- **Interaction graph:** `verifySubscription` middleware fires on every write request to projects and sync routes → queries Supabase `subscriptions` table → adds ~50ms latency per gated request.
- **Error propagation:** 403 from backend → caught by `CloudSyncContext` and project settings → shows upgrade prompt. Need to ensure all callers handle this error code.
- **State lifecycle risks:** If webhook delivery fails after checkout, the subscription row stays `pending` and the user can't access paid features. The existing retry logic in `AuthContext` (4 attempts x 2s) handles the delay, but a permanently failed webhook would require manual intervention.
- **API surface parity:** Both `create-checkout-session` and `create-subscription-intent` endpoints need valid price IDs. Currently only the embedded Elements flow is used by the UI.
